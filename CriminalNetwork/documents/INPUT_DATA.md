# INPUT DATA — What We Receive

> We don't know what data will come. This document defines every possible input, every field, every format, every messiness, every edge case. When data arrives, we check it against this document.

## Stage → Model Mapping

This document defines inputs for the five analytical models (see SYSTEM_STRUCTURE.md). Each stage contributes to one or more models:

```
Stage 1: Ingestion     → Model 1: Evidence Model
Stage 2: Extraction    → Model 1: Evidence Model
Stage 3: Resolution    → Model 2: Provenance + Model 3: Coverage + Model 4: Entity State
Stage 4: Temporal      → Model 2: Provenance + Model 3: Coverage
Stage 5: Graph Build   → Model 4: Entity State + Model 5: Hypothesis
Stage 6: Analytics     → Model 5: Hypothesis & Investigation
Stage 7: Hypothesis    → Model 5: Hypothesis & Investigation
Stage 8: Contradiction → Model 5: Hypothesis & Investigation
Stage 9: Gap Detection → Model 5: Hypothesis & Investigation
Stage 10: Critic       → Reads ALL models (read-only), writes audit
```

## 0. Source-Origin Epistemic Contract

Every piece of data entering the system has properties that must be captured at ingestion. These are NOT the same thing, and collapsing them causes investigative errors.

### The Six Properties

```
SOURCE: Where did this data come from?
├── carrier (automated, high reliability for occurrence)
├── bank (automated, high reliability for occurrence)
├── police officer (manual, medium reliability)
├── intelligence agent (manual, low-medium reliability)
├── news article (derived, low reliability)
├── social media (unverified, low reliability)
└── witness statement (manual, low reliability)

OBSERVATION: What did someone directly see/record?
├── CDR: "A called B at 14:32" — automated observation
├── Bank: "₹2,00,000 transferred from A to B" — automated observation
├── CCTV: "Person matching description entered building" — automated observation
├── Surveillance: "Subject met with unknown male" — human observation
└── FIR narrative: "Accused called victim" — human claim about observation

CLAIM: What does the source assert is true?
├── FIR: "Accused cheated complainant of ₹2,00,000" — LEGAL CLAIM
├── FIR: "Accused called on mobile number 9876543210" — CLAIM ABOUT FACT
├── Surveillance: "Subject appeared nervous" — SUBJECTIVE CLAIM
├── Social media: "Great meeting today" — SELF-REPORTED CLAIM
└── News article: "Police say suspect is linked to fraud ring" — SECONDHAND CLAIM

DERIVED INFORMATION: What was computed/inferred from other data?
├── ML entity extraction: "This name refers to Person X" — INFERENCE
├── Anomaly detection: "Activity burst detected" — COMPUTATION
├── Hypothesis: "A and B may be coordinating" — REASONING
└── News article summarizing FIR: DERIVED, not original

PROVENANCE CLASS: What epistemic category does this data belong to?
├── OBSERVATIONAL: Directly observed by sensor or person
├── DERIVED: Computed from observational data
├── INVESTIGATIVE: Generated by investigation process
└── MODEL_GENERATED: Produced by ML or reasoning system

VERIFICATION STATUS: How well is this data verified?
├── UNVERIFIED: No independent verification
├── CORROBORATED: Consistent with other data
├── INDEPENDENTLY_VERIFIED: Verified by independent source
└── LEGALLY_ESTABLISHED: Established by court or authoritative proceeding
```

### Why Provenance ≠ Verification

```
DANGEROUS:
  provenance_class = GROUND_TRUTH

  This conflates two questions:
  ├── "Where did this data come from?" (provenance)
  └── "How well is this data verified?" (verification)

  A court record and a biometric match are both "verified"
  but have radically different epistemic meanings.

SAFE:
  provenance_class = OBSERVATIONAL
  verification_status = INDEPENDENTLY_VERIFIED

  Now we know:
  ├── This is an observation (not derived or model-generated)
  └── It has been independently verified (not just corroborated)

EXAMPLE:
  Court record: "Person X committed offense"
  ├── provenance_class: OBSERVATIONAL (court proceeding)
  └── verification_status: LEGALLY_ESTABLISHED (court verdict)

  Biometric match: "Person X is the person in image"
  ├── provenance_class: MODEL_GENERATED (biometric system)
  └── verification_status: CORROBORATED (consistent with other data)

  Police database: "Person X committed offense"
  ├── provenance_class: DERIVED (database record)
  └── verification_status: UNVERIFIED (no independent check)

  These are three very different things.
  Collapsing them into "ground truth" is dangerous.
```

### Critical Rule: Ground Truth Is Not a Provenance Class

```
RULE: "GROUND_TRUTH" must never appear as a provenance_class.

WHY:
├── Investigator conclusion marked "verified" → GROUND_TRUTH
│   → Training data
│   → Model learns pattern
│   → Circular reasoning

├── Investigator hypotheses must not become labels.
│   "H1: X is involved" is a hypothesis, not a label.
│   Only confirmed outcomes become verification_status = LEGALLY_ESTABLISHED.

├── "Human reviewed" can accidentally become "ground truth."
│   Review ≠ verification. Reviewer may be wrong.

└── The system must distinguish:
    ├── What was observed (provenance)
    ├── How well it's verified (verification)
    └── Never conflate the two
```

### Verification Status Rules

```
UNVERIFIED:
├── Default for new data
├── Cannot be used as training truth
├── Can support hypotheses but with low weight
└── Must be flagged as unverified in all outputs

CORROBORATED:
├── Consistent with other data
├── May support hypotheses with moderate weight
├── Cannot be used as training truth without independent verification
└── Must note what corroborates it

INDEPENDENTLY_VERIFIED:
├── Verified by independent source
├── Can support hypotheses with high weight
├── Can be used as training truth with caution
└── Must note independent verifier

LEGALLY_ESTABLISHED:
├── Established by court or authoritative proceeding
├── Can support hypotheses with highest weight
├── Can be used as training truth
└── Must note legal proceeding and date
```

### Why This Matters

```
EXAMPLE: Three files arrive

File 1: FIR #1234
├── SOURCE: Police officer (manual, medium reliability)
├── OBSERVATION: Officer interviewed complainant
├── CLAIM: "Accused Rakesh cheated complainant"
├── DERIVED: None (original document)
└── PROVENANCE: OBSERVATIONAL

File 2: News article about FIR #1234
├── SOURCE: Newspaper (derived, low reliability)
├── OBSERVATION: Reporter read FIR
├── CLAIM: "Rakesh arrested for ₹2 lakh fraud"
├── DERIVED: From FIR #1234 (DEPENDENT)
└── PROVENANCE: DERIVED

File 3: Social media post about FIR #1234
├── SOURCE: Social media user (unverified, low reliability)
├── OBSERVATION: User saw news article
├── CLAIM: "Rakesh is a fraudster"
├── DERIVED: From news article (DEPENDENT)
└── PROVENANCE: DERIVED

WITHOUT EPISTEMIC CONTRACT:
└── System sees 3 sources confirming Rakesh is fraudster
    → Confidence artificially inflated

WITH EPISTEMIC CONTRACT:
├── File 1: Original observation (independent)
├── File 2: Derived from File 1 (DEPENDENT)
├── File 3: Derived from File 2 (DEPENDENT)
└── System sees 1 independent source + 2 derivatives
    → Confidence based on 1 source, not 3
```

## 0.1 Claim-Aware Dependency DAG

The previous design used flat `dependency_group_id`. That is too coarse. Real investigations have partial dependency at the claim level.

### The Problem With Flat Groups

```
FIR #1234 contains:
├── Claim A: "Witness saw Rakesh at hotel" (from witness statement)
├── Claim B: "CCTV shows person entering" (from CCTV footage)
├── Claim C: "Officer observed meeting" (from officer report)

News article summarizes Claim A + Claim B.

Flat dependency_group treats entire FIR as one source.
But Claim A (witness) and Claim B (CCTV) have DIFFERENT sub-sources.
They are partially independent even though they share a document.
```

### Claim-Aware Dependency Model

```
EvidenceItem {
  id:                string
  
  // DEPENDENCY DAG
  source_id:         string      // which RawEvidence produced this
  claim_id:          string      // which specific claim this supports
  derived_from:      string[]    // EvidenceItem IDs this depends on
  dependency_type:   DependencyType  // HOW it depends on source
  
  // CONTENT
  content:           object      // the actual evidence
  confidence:        ConfidenceDecomposition  // typed + explained
}

DependencyType:
├── DIRECT_OBSERVATION   // sensor/person directly recorded this
├── DERIVED              // computed from other evidence
├── QUOTED               // source reports what another source said
├── SUMMARIZED           // source condenses original content
├── INFERRED             // reasoning system concluded this
└── DUPLICATED           // same information in different form
```

### DAG Example

```
RAW SOURCES:
├── witness_17: "Saw Rakesh at hotel" (DIRECT_OBSERVATION)
├── cctv_04: "Person entering building" (DIRECT_OBSERVATION)
├── officer_12: "Observed meeting" (DIRECT_OBSERVATION)
└── news_01: "Summarizes witness + CCTV" (SUMMARIZED from witness_17 + cctv_04)

DEPENDENCY DAG:
witness_17 ──→ fir_claim_A ──→ news_01
cctv_04 ────→ fir_claim_B ──→ news_01
officer_12 ──→ fir_claim_C

INDEPENDENCE ANALYSIS for "Rakesh at hotel":
├── fir_claim_A depends on witness_17
├── fir_claim_B depends on cctv_04
├── fir_claim_C depends on officer_12
├── news_01 depends on witness_17 + cctv_04
└── INDEPENDENT SOURCES: 3 (witness_17, cctv_04, officer_12)
    NOT 4 (news_01 is dependent)

INDEPENDENCE ANALYSIS for "Rakesh at hotel" using ONLY fir_claim_A + news_01:
├── fir_claim_A depends on witness_17
├── news_01 depends on witness_17 + cctv_04
└── INDEPENDENT SOURCES: 1 (witness_17)
    Because news_17 and fir_claim_A share witness_17
```

### Independence Calculation

```
FUNCTION: count_independent_sources(evidence_ids[], hypothesis)
├── input: evidence IDs supporting a hypothesis
├── process:
│   ├── For each evidence item, trace dependency DAG to root sources
│   ├── Group by root source
│   ├── Count unique root sources (NOT evidence items)
│   └── This is the independent source count
├── output: independent_source_count
└── this is the TRUE basis for hypothesis confidence

RULE: Evidence from same root source cannot corroborate each other
      regardless of how many intermediate documents exist.
```

### Dependency Type Semantics

```
DIRECT_OBSERVATION:
├── Highest weight
├── Independence: full (if from different sensor/person)
└── Example: CDR record, CCTV footage, bank transaction

DERIVED:
├── Weight depends on derivation quality
├── Independence: inherits from source
└── Example: ML entity extraction, computed anomaly score

QUOTED:
├── Weight = source reliability × quoted source reliability
├── Independence: depends on quoted source
└── Example: News article quoting police

SUMMARIZED:
├── Weight = source reliability × summary accuracy
├── Independence: depends on original source
└── Example: News article summarizing FIR

INFERRED:
├── Weight depends on inference model quality
├── Independence: depends on input evidence
└── Example: Hypothesis generated by reasoning system

DUPLICATED:
├── Weight = same as original
├── Independence: same as original (NOT independent)
└── Example: Same CDR record from two different providers
```

## 0.2 Contextual Source Reliability

Source reliability is NOT a single number. It depends on what claim the source is supporting, the acquisition context, and the source's condition.

### The Problem With Single Reliability

```
DANGEROUS:
  "CCTV reliability = 0.90"

This implies CCTV is universally 90% reliable.
But CCTV is:
├── Strong for: "person appeared at location" (0.90)
├── Weak for: "person is definitely X" (0.50 if poor quality)
├── Weak for: "person intended Y" (0.0 — CCTV cannot read intent)
└── Irrelevant for: "conversation contained Z" (CCTV has no audio)
```

### Contextual Reliability Model

```
ReliabilityAssessment {
  source_type:        string      // "cdr" / "cctv" / "fir" / etc.
  claim_type:         string      // what category of claim
  reliability:        float       // 0-1, conditional on context
  
  // CONTEXT DIMENSIONS (optional, for precision)
  acquisition_context: string     // "automated" / "human_observed" / "human_reported"
  source_condition:   string      // "verified_functional" / "assumed_functional" / "unknown"
  temporal_distance:  string      // "real_time" / "hours" / "days" / "weeks" / "unknown"
  attribution_quality: string     // "verified" / "moderate" / "low" / "not_applicable"
  
  // BASIS (always required — explain WHY this reliability)
  basis:              string[]    // ["timestamp verified", "image quality high", etc.]
}

SourceReliabilityMatrix {
  // Entry: source_type × claim_type → ReliabilityPolicy
  
  "cdr": {
    "occurrence":    ReliabilityPolicy { ... },
    "identity":      ReliabilityPolicy { ... },
    "location":      ReliabilityPolicy { ... },
    "possession":    ReliabilityPolicy { ... },
    "intent":        ReliabilityPolicy { ... },
    "content":       ReliabilityPolicy { ... }
  },
  
  "cctv": { ... },
  "fir": { ... },
  "surveillance": { ... }
  
  // ... other source types
}

ReliabilityPolicy {
  value:            float       // 0-1, the reliability estimate
  
  // CALIBRATION — WHERE DID THIS NUMBER COME FROM?
  basis:            string[]    // ["automated", "timestamp verified"]
  source:           string      // "expert_consultation" / "empirical_study" / "industry_standard" / "assumption"
  version:          string      // "v1.0" — policies versioned
  applicable_context: string    // when this policy applies
  
  // VALIDATION — HAS THIS BEEN TESTED?
  empirical_validation: EmpiricalValidation
}

EmpiricalValidation {
  validated:        boolean     // has this been empirically tested?
  sample_size:      int         // how many observations?
  accuracy:         float       // measured accuracy against ground truth
  confidence_interval: float    // 95% CI
  last_validated:   datetime    // when last tested
  validation_source: string     // study or dataset used
  
  // IF NOT VALIDATED
  validation_status: string     // "validated" / "partially_validated" / "assumed" / "not_applicable"
  assumption_risk:  string      // "low" / "medium" / "high"
}
```

### Why Calibration Matters

```
DANGEROUS:
  "CDR occurrence = 0.95"
  
  Investigator asks: "Where did 0.95 come from?"
  Answer: "Expert assumption."
  
  This is expert assumption disguised as probability.
  System uses it for ML reasoning.
  Results look authoritative but are unvalidated.

SAFE:
  ReliabilityPolicy {
    value: 0.95
    basis: ["automated record", "timestamp verified", "provider-managed"]
    source: "industry_standard"
    version: "v1.0"
    applicable_context: "CDR from major Indian carriers, post-2020"
    empirical_validation: {
      validated: true,
      sample_size: 10000,
      accuracy: 0.94,
      confidence_interval: 0.02,
      last_validated: "2024-01-15",
      validation_source: "TRAI CDR accuracy study 2023"
    }
  }
  
  Now the investigator can see:
  ├── The value (0.95)
  ├── Where it came from (industry standard)
  ├── How it was validated (empirical study)
  ├── How confident we are (±0.02)
  └── When it was last tested (2024-01-15)
```

### Reliability Policy Rules

```
RULE 1: Every reliability value must be backed by a ReliabilityPolicy.
        No bare numbers without calibration.

RULE 2: Policies must be versioned.
        When evidence arrives, note which policy version was used.

RULE 3: Empirical validation is preferred but not always possible.
        If not validated:
        ├── Mark as "assumed"
        ├── Note assumption_risk
        └── Flag for future validation

RULE 4: Policies must be reviewed periodically.
        Old policies may not apply to new data sources.

RULE 5: When exposing reliability to investigator:
        ├── Show value
        ├── Show basis
        ├── Show source (expert/empirical/standard)
        ├── Show validation status
        └── Show last validation date

RULE 6: Adversarial detection mapping
        Source type → adversarial risk profile
        ├── CDR: Low adversarial risk (automated, hard to manipulate)
        ├── Bank: Low adversarial risk (automated, regulated)
        ├── CCTV: Medium adversarial risk (can be tampered)
        ├── Surveillance: Medium adversarial risk (human observation)
        ├── FIR: Medium adversarial risk (human report)
        ├── News article: High adversarial risk (derived, manipulated)
        ├── Social media: High adversarial risk (unverified, manipulated)
        └── Witness statement: Medium adversarial risk (human memory)
```

### Reliability Exposure Rule

```
RULE: Never expose a bare reliability number to the investigator.

BAD:
  "CCTV reliability = 0.90"

GOOD:
  CCTV-17
  claim: person_at_location
  reliability: 0.86
  basis:
      + timestamp verified
      + image quality high
      + camera position confirmed
      - identity match moderate (face partially obscured)
  calibration:
      source: empirical_study
      validated: true
      accuracy: 0.88
      last_validated: 2024-02-01

The investigator can evaluate whether the basis supports the reliability.
```

### Contextual Reliability Lookup

```
FUNCTION: get_reliability(source_type, claim_type, context)
├── input: source type, claim type, optional context
├── process:
│   ├── Look up base reliability from matrix
│   ├── Adjust for context dimensions if provided
│   └── Return ReliabilityAssessment with basis
├── output: ReliabilityAssessment
└── basis ALWAYS required — no reliability without justification

IF context not provided:
└── Use base reliability from matrix (less precise, but honest)

IF context provided:
└── Adjust reliability based on conditions
    Example: CCTV with poor lighting → reduce identity reliability
```

### Dependency Group Assignment at Ingestion

```
RULE: Every RawEvidence is assigned a dependency_group at ingestion.

IF derived_from is empty (original document):
├── dependency_group = own ID (independent)
└── This is a root source

IF derived_from is not empty (derived document):
├── dependency_group = dependency_group of first derived_from
└── This shares dependency group with its source

EXAMPLE:
RawEvidence raw_001 (FIR #1234):
├── derived_from: []
├── dependency_group: "raw_001"
└── INDEPENDENT

RawEvidence raw_002 (news article about FIR #1234):
├── derived_from: ["raw_001"]
├── dependency_group: "raw_001"
└── DEPENDENT (shares group with FIR)

RawEvidence raw_003 (social media about news article):
├── derived_from: ["raw_002"]
├── dependency_group: "raw_001"
└── DEPENDENT (shares group with FIR, through news)

RULE: Evidence from same dependency_group cannot corroborate each other.
      They share the same root source.
```

## 0.4 Source Integrity

Source integrity asks a different question than reliability. Reliability asks: "How trustworthy is this source for this claim?" Integrity asks: "Can we establish that this evidence is what it claims to be and hasn't been improperly altered?"

### The Problem

```
CCTV.mp4 arrives in system.

Questions the investigator needs answered:
├── Was the file altered?
├── Was the timestamp preserved?
├── Was metadata modified?
├── Was it transcoded?
├── Was there a gap in recording?
├── Is the extracted frame representative?
├── Was chain-of-custody preserved?
└── Who handled this file?

CDR.csv arrives in system.

Questions:
├── Is this original provider export?
├── Was it manually compiled?
├── Was it converted from another format?
├── Was it filtered by analyst?
├── What transformation history?
└── Who touched this file?

These are different evidentiary objects.
```

### Source Integrity Model

```
EvidenceIntegrity {
  id:                string
  
  // ACQUISITION
  acquisition_method: string      // "direct_provider_export" / "legal_request" / "manual_collection" / "open_source"
  acquisition_chain:  string[]    // who handled this evidence ["carrier_API", "investigator", "system"]
  
  // FORMAT
  original_format:   string      // original file format when collected
  current_format:    string      // format as received by system
  format_changed:    boolean     // was format converted?
  
  // HASH
  content_hash:      string      // SHA-256 of content as received
  metadata_hash:     string      // hash of metadata
  original_hash:     string      // hash at time of collection (if known)
  
  // CHAIN OF CUSTODY
  chain_of_custody:  ChainOfCustody
  
  // TRANSFORMATION
  transformation_history: Transformation[]
  
  // INTEGRITY STATUS
  integrity_status:  IntegrityStatus
}

ChainOfCustody {
  preserved:         boolean     // was chain of custody maintained?
  handlers:          Handler[]   // who handled this evidence
  gaps:              string[]    // gaps in custody chain
  
  // IF NOT PRESERVED
  custody_gaps:      string[]    // where chain is broken
  impact:            string      // how this affects evidence value
}

Handler {
  handler_id:        string      // who handled it
  role:              string      // "collector" / "analyst" / "system" / "investigator"
  time_handled:      datetime    // when
  action_taken:      string      // what they did
}

Transformation {
  transformation_type: string    // "format_conversion" / "extraction" / "filtering" / "compression" / "enhancement"
  input_format:      string
  output_format:     string
  performed_by:      string      // who did it
  performed_at:      datetime
  reversible:        boolean     // can original be reconstructed?
  lossy:             boolean     // was information lost?
}

IntegrityStatus {
  status:            string      // "verified" / "suspect" / "compromised" / "unknown"
  
  // VERIFIED
  // Chain of custody intact, hashes match, no unauthorized modifications
  
  // SUSPECT
  // Minor issues detected, may still be usable
  // Example: format conversion, transcoding
  
  // COMPROMISED
  // Major issues detected, evidence may be unreliable
  // Example: chain of custody broken, hashes don't match
  
  // UNKNOWN
  // Cannot verify integrity
  // Example: no chain of custody, no original hash
  
  issues:            string[]    // specific integrity issues detected
  impact:            string      // how integrity issues affect evidence value
}
```

### Integrity vs Reliability

```
CCTV.mp4:
├── Reliability: 0.90 for "person at location"
│   └── Camera was functional, timestamp verified
│
├── Integrity: SUSPECT
│   └── File was transcoded from MP4 to AVI
│       Chain of custody has gap (2 hours unaccounted)
│       Original hash unknown
│
└── These are DIFFERENT problems.
    Reliable source with compromised integrity.
    Investigator needs to know BOTH.
```

### Integrity Rules

```
RULE 1: Every evidence item must have an EvidenceIntegrity record.
        If integrity cannot be verified, mark as "unknown" with explanation.

RULE 2: Integrity issues must be reported alongside reliability.
        "CCTV reliable for location (0.90) but integrity suspect (transcoded, custody gap)."

RULE 3: Compromised integrity reduces effective reliability.
        effective_reliability = reliability × integrity_factor
        Where integrity_factor:
        ├── verified: 1.0
        ├── suspect: 0.8
        ├── compromised: 0.5
        └── unknown: 0.7

RULE 4: Chain of custody gaps must be documented.
        "Evidence handled by: carrier_API → investigator_john → system"
        "Gap: 2 hours between carrier export and investigator receipt"

RULE 5: Lossy transformations must be noted.
        "CCTV frame extracted from video. Original video not preserved."
        "Audio content lost in CDR extraction."
```

## 0.3 Search Completeness Tracking

"NOT_FOUND" does not mean "DOES_NOT_EXIST." The system must distinguish between absence of evidence and evidence of absence.

### The Problem

```
EXAMPLE:
Phone records searched → NOT_FOUND

This could mean:
├── Phone records don't exist
├── Searched wrong date range
├── Searched wrong identifier
├── Searched wrong provider
├── Searched one database but records exist elsewhere
├── Records were destroyed
├── Records exist but access was denied
└── Search was inadequate

Without tracking search completeness:
└── NOT_FOUND accidentally becomes DOES_NOT_EXIST
    → Hypothesis involving phone records gets weakened
    → Investigator stops looking
    → Real evidence missed
```

### Search Completeness Model

```
SearchRecord {
  id:                string
  evidence_gap_id:   string      // which EvidenceGap this addresses
  
  // WHAT WAS SEARCHED
  search_target:     string      // "phone_records_Suresh_Jan2024"
  evidence_type:     string      // "cdr" / "bank" / "cctv" / etc.
  
  // HOW IT WAS SEARCHED
  search_scope:      SearchScope
  search_method:     string      // "database_query" / "legal_request" / "manual_review" / "api_call"
  search_quality:    string      // "comprehensive" / "targeted" / "preliminary" / "incomplete"
  
  // RESULT
  result:            string      // "FOUND" / "NOT_FOUND" / "PARTIAL" / "UNAVAILABLE" / "DENIED"
  result_detail:     string      // explanation of what was found/not found
  
  // COMPLETENESS ASSESSMENT
  completeness:      SearchCompleteness
  
  // METADATA
  searched_by:       string      // who/what performed search
  searched_at:       datetime
  search_duration:   duration
}

SearchScope {
  time_range:        string      // "Jan 2024" / "2024-01-01 to 2024-01-31" / "unknown"
  identifiers:       string[]    // ["9876543210", "9876543211"]
  providers:         string[]    // ["Airtel", "Jio"] or ["all known"]
  databases:         string[]    // ["CDR_database", "bank_database"]
  geographic_scope:  string      // "national" / "state" / "district" / "unknown"
}

SearchCompleteness {
  coverage_ratio:    float       // 0-1, how thorough was the search
  confidence:        float       // 0-1, how confident are we in completeness
  
  gaps_in_search:    string[]    // what we DIDN'T search
  limitations:       string[]    // why search may be incomplete
  
  // ASSESSMENT
  assessment:        string      // "comprehensive" / "adequate" / "partial" / "minimal"
}
```

### Search Completeness Examples

```
EXAMPLE 1: Comprehensive search
SearchRecord {
  search_target: "phone_records_Suresh_Jan2024"
  search_scope: {
    time_range: "2024-01-01 to 2024-01-31",
    identifiers: ["9876543210"],
    providers: ["all known"],
    databases: ["CDR_database", "carrier_API"]
  }
  result: "NOT_FOUND"
  completeness: {
    coverage_ratio: 0.95,
    confidence: 0.90,
    gaps_in_search: ["prepaid numbers not linked to ID"],
    limitations: ["carrier API may have 24-hour delay"],
    assessment: "comprehensive"
  }
}
→ NOT_FOUND is meaningful. Evidence likely doesn't exist.

EXAMPLE 2: Incomplete search
SearchRecord {
  search_target: "phone_records_Suresh_Jan2024"
  search_scope: {
    time_range: "2024-01-15 to 2024-01-31",
    identifiers: ["9876543210"],
    providers: ["Airtel"],
    databases: ["CDR_database"]
  }
  result: "NOT_FOUND"
  completeness: {
    coverage_ratio: 0.40,
    confidence: 0.50,
    gaps_in_search: ["Jan 1-14", "other providers", "prepaid numbers"],
    limitations: ["only searched postpaid", "only one provider"],
    assessment: "partial"
  }
}
→ NOT_FOUND is NOT meaningful. Search was inadequate.
  Investigator should search remaining scope before concluding.
```

### Negative Evidence Semantics

```
RULE: Absence of evidence must never automatically become evidence of absence.

The system must distinguish:

CONFIRMED_ABSENCE:
├── Search was comprehensive
├── Coverage ratio > 0.80
├── Confidence > 0.80
├── Result: NOT_FOUND
└── Meaning: Evidence likely does not exist

UNCONFIRMED_ABSENCE:
├── Search was partial or minimal
├── Coverage ratio < 0.80
├── OR confidence < 0.80
├── Result: NOT_FOUND
└── Meaning: Evidence may exist but wasn't found

UNKNOWN:
├── No search performed
├── Result: UNKNOWN
└── Meaning: We don't know if evidence exists

UNAVAILABLE:
├── Search performed but access denied
├── Result: DENIED
└── Meaning: Evidence exists but we can't access it

DESTROYED:
├── Evidence known to have existed but was destroyed
├── Result: DESTROYED
└── Meaning: Evidence existed but is no longer available

RULE: The Critic must never use UNCONFIRMED_ABSENCE to weaken a hypothesis.
      Only CONFIRMED_ABSENCE can legitimately weaken a hypothesis.
```

### Negative Evidence in Hypothesis Reasoning

```
EXAMPLE:
Hypothesis H1: "Rakesh and Suresh coordinated fraud"

Negative evidence: "No phone records found between Rakesh and Suresh"

IF search was comprehensive (CONFIRMED_ABSENCE):
├── H1 confidence: decrease moderately
├── Reason: Expected communication not found
└── BUT: They could communicate through other means

IF search was partial (UNCONFIRMED_ABSENCE):
├── H1 confidence: DO NOT DECREASE
├── Reason: Search was inadequate
└── Action: Complete search before drawing conclusions

RULE: UNCONFIRMED_ABSENCE is treated as UNKNOWN, not as negative evidence.
```

```

District:          e.g., "Guna"
```

| district | string | "Guna" | May be misspelled |
| state | string | "Madhya Pradesh" | May be "MP" or full name |
| date_of_offence | date | "15/03/2024" | DD/MM/YYYY or MM/DD/YYYY |
| date_of_report | date | "16/03/2024" | Same format issues |
| complainant_name | string | "Rajesh Singh" | May have typos |
| complainant_father | string | "Ram Singh" | May be missing |

| accused_name | string | "Rakesh alias Raki" | Aliases embedded in name |
| accused_father | string | "Ram Kumar" | May be missing |

| narrative | string | (long text) | Hindi/English mix, abbreviations |
| witnesses | string[] | ["Mohan Kumar", "Suresh"] | May be empty |
| property | string | "Rs. 2,00,000/-" | Indian number format |

### Messiness We'll Encounter

```
1. LANGUAGE MIX
   "accused Rakesh ne Suresh ko phone kiya aur 
    uske account mein ₹2 lakh transfer kiye"
   → Hindi + English in same sentence

2. ABBREVIATIONS
   "u/s 420/468/120B IPC" = "under section 420/468/120B IPC"
   "r/o" = "resident of"
   "s/o" = "son of"
   "d/o" = "daughter of"
   "w/o" = "wife of"
   "PS" = "Police Station"
   "Distt." = "District"

3. NAME VARIATIONS
   "Rakesh" / "Rakesh Kumar" / "R. Kumar" / "Rakesh s/o Ram Kumar"
   Same person, different representations

4. ADDRESS VAGUENESS
   "near Hotel Taj" — which Taj? Which city?
   "Guna" — district or city?

5. TIME IMPRECISION
   "Between 14:00 and 16:00" — 2-hour window
   "afternoon" — no specific time
   "on 15/03/2024" — no time at all

6. OCR ERRORS (scanned FIRs)
   "Rakesh" → "Rake$h" or "Rak3sh"
   "9876543210" → "987654321O" (O instead of 0)
   "Hotel Taj" → "H0tel Taj"

7. MISSING FIELDS
   Complainant phone may be missing
   Accused address may be missing
   Witnesses may be listed as "unknown"

8. CONFLICTING INFO
   Date of offence in header says 15/03
   Narrative says "on 14/03/2024"
   → Which is correct?
```

|-------|------|---------|-----------|

| call_date | date | "2024-01-15" | YYYY-MM-DD usually |
| call_time | time | "14:32:00" | HH:MM:SS |

| type | string | "LOCAL" | May be missing |

```
   Number appears for 2 weeks, then disappears
   → Temporary communication channel

4. TOWER GRANULARITY
   Tower covers 1-3km radius
   "Near Hotel Taj" doesn't mean "at Hotel Taj"
   → Location is approximate

5. TIMESTAMP ISSUES
   Carrier server time vs actual call time
   Timezone not specified
   → May be off by hours

6. MISSING RECORDS
   Carrier only retains 90 days
   Older records purged
   → Gaps in timeline

7. ANONYMIZED NUMBERS
   Some numbers masked as "XXXXX1234"
   → Can't trace full number
```

```
   "2,00,000" (Indian) vs "200000" (standard)
   → Parse carefully

7. SETTLEMENT LAG
   NEFT settles T+1
   → Transaction date ≠ settlement date
```

## 11. Edge Cases We Must Handle

### Edge Case 1: Same Name, Different People

```
"Rahul Kumar" in FIR #1234 (accused)
"Rahul Kumar" in FIR #5678 (complainant)
Same name? Different people?

RESOLUTION: Cross-reference with:
├── Father's name
├── Address
├── Phone number
├── Vehicle number
└── Age/DOB
```

### Edge Case 2: Same Phone, Different People

```
Phone 9876543210:
├── CDR 2023: Used by Person A
├── CDR 2024: Used by Person B
├── SIM registration: Person A
└── Behavioral analysis: Person B

RESOLUTION: Track phone lifecycle:
├── active_period: {from, until}
├── registered_to: Person
├── observed_users: Person[]
└── Last known user: Person B
```

### Edge Case 3: Missing Data

```
FIR says "Rakesh called 9876543210"
CDR shows: No record of this call

POSSIBLE REASONS:
├── CDR data incomplete (carrier didn't provide)
├── Call was on different SIM
├── Call was via WhatsApp (not in CDR)
├── FIR narrative is wrong
└── Call record was deleted

HANDLING: Don't create edge. Flag as "FIR CLAIM, NO CDR CONFIRMATION"
```

### Edge Case 4: Conflicting Data

```
FIR: "Meeting at Hotel Taj on 15/03/2024"
CDR: "Phone in Bhopal on 15/03/2024"
CCTV: "Subject at Hotel Taj on 15/03/2024"

CONTRADICTION: CDR says Bhopal, FIR + CCTV say Guna

RESOLUTION: 
├── CDR shows phone location, not person location
├── Phone could be with someone else
├── FIR and CCTV agree → higher weight
└── Flag as CONTRADICTION, don't resolve
```

### Edge Case 5: Encrypted/Deleted Data

```
WhatsApp messages: Encrypted, can't read
Deleted SMS: Partially recovered
Social media: Some posts deleted

HANDLING:
├── Note what's available vs what's missing
├── Don't assume deleted = doesn't exist
├── Track data completeness per source
└── Flag gaps in coverage model
```

### Edge Case 6: Multi-Language Text

```
FIR narrative: "accused Rakesh ne Suresh ko phone 
kiya aur uske account mein ₹2 lakh transfer kiye. 
Dono ne mil ke Hotel Taj mein meeting ki."

Hindi + English in same sentence.

HANDLING:
├── Use multilingual NER (IndicBERT or similar)
├── Transliterate to English for processing
├── Track language per document
└── Flag low-confidence extractions
```

### Edge Case 7: Indian Number Format

```
Amount: "2,00,000" = 200000
Amount: "10,00,000" = 1000000
Amount: "₹50,000" = 50000

HANDLING:
├── Parse Indian comma format (lakhs/crores)
├── Remove currency symbols
├── Standardize to numeric
└── Track original format for audit
```

### Edge Case 8: Date Format Confusion

```
"03/04/2024" = March 4 or April 3?

In India: DD/MM/YYYY (March 4)
In US: MM/DD/YYYY (April 3)

HANDLING:
├── Assume DD/MM/YYYY for Indian data
├── Cross-reference with other dates in same document
├── Flag ambiguous dates
└── Use context to resolve
```

## 12. Adversarial Data Scenarios

Data may be intentionally manipulated to mislead analysis.

### Scenario 1: Framing

```
Criminal creates fake communication trail:
├── Sends SMS from victim's phone to associate
├── Makes call from victim's phone to known criminal
├── Creates bank transfer from victim's account
└── Result: Victim appears connected to criminal network

HANDLING:
├── Check source reliability
├── Check behavioral consistency
├── Check temporal consistency
└── Flag suspicious patterns
```

### Scenario 2: Misdirection

```
Criminal creates noise to hide real relationships:
├── Makes many calls to decoy numbers
├── Creates transactions with shell companies
├── Generates fake social media activity
└── Result: Real relationships buried in noise

HANDLING:
├── Filter by source reliability
├── Check behavioral consistency
├── Look for natural vs artificial patterns
└── Focus on high-confidence edges
```

### Scenario 3: Identity Manipulation

```
Criminal uses multiple identities:
├── Same person appears as "Rakesh," "R. Kumar," "Raki"
├── Different addresses, different phones
├── Creates illusion of network size
└── Result: One person appears as multiple people

HANDLING:
├── Probabilistic identity resolution
├── Cross-reference all attributes
├── Don't force merge or force separate
└── Track uncertainty
```

### Scenario 4: Evidence Planting

```
Criminal plants evidence to implicate innocent person:
├── Leaves victim's物品 at crime scene
├── Uses victim's phone near crime scene
├── Creates financial trail through victim's accounts
└── Result: Innocent person appears guilty

HANDLING:
├── Check evidence consistency
├── Check behavioral patterns
├── Check opportunity (was person actually there?)
└── Don't rely on single evidence type
```

## 13. Cross-Case Contamination

Entities appearing in multiple cases do not automatically connect the cases.

### The Problem

```
Case 1: Rakesh involved in fraud
Case 2: Suresh involved in drug trafficking

Rakesh and Suresh know each other (CDR shows calls).

DOES THIS MEAN FRAUD AND DRUG TRAFFICKING ARE CONNECTED?

NOT NECESSARALLY:
├── Rakesh and Suresh may be cousins (social tie)
├── Their criminal activities may be completely separate
├── The phone calls may be about family matters
└── Connecting cases without evidence is contamination

HANDLING:
├── Each case has its own hypothesis space
├── Shared entities are noted but not automatically linked
├── Cross-case connections require independent evidence
└── Don't let one case's evidence contaminate another
```

### Case Scoping

```
RULE: Evidence is case-scoped.

Case 1 evidence:
├── FIR #1234
├── CDR for Rakesh
├── Bank records for Rakesh
└── Surveillance of Rakesh-Suresh meeting

Case 2 evidence:
├── FIR #5678
├── CDR for Suresh
├── Bank records for Suresh
└── Surveillance of Suresh-Mohan meeting

Shared entity: Rakesh-Suresh connection
├── NOT automatically evidence for Case 1 or Case 2
├── Only evidence: they communicate
├── Communication content unknown
└── Don't assume criminal coordination
```
